# запуск в production

Текущий этап — локально проверенный backend с WebM-видеостикерами и миграциями
001–026. Перед публичным запуском нужно завершить эксплуатацию медиа, проверить
realtime на целевом окружении и подготовить production-контур.
Порядок этапов описан в [README](../README.md#ближайший-план).

## что уже можно подготовить

1. Создай отдельного пользователя PostgreSQL с минимальными правами и отдельную
   Redis database
2. Укажи `APP_ENV=production` и `APP_DEBUG=false`
3. Примени миграции командой `python -m scripts.migrate`. Для текущего backend
   последняя миграция — `026_realtime_outbox`. Перед запуском записи выполни
   первичную инвентаризацию по инструкции ниже
4. Настрой HTTPS на reverse proxy и не открывай uvicorn в интернет напрямую
5. Включи резервные копии PostgreSQL и закрытого каталога медиа. Регулярно
   проверяй согласованное восстановление базы и файлов в отдельном окружении
6. Настрой worker, таймер очистки и таймер мониторинга по инструкции ниже

## worker, очистка и мониторинг

Шаблоны доступны в `main3` с `9ac06be`. В WSL проверены синтаксис unit-файлов,
восстановление worker и очистка после повторной обработки. На целевом сервере
проверь запуск таймеров, записи в journald и выдачу через Nginx.

После инвентаризации скопируй примеры из `deploy/` в `/etc/systemd/system/`,
убрав суффикс `.example`. В `imageboard-media-worker.service`,
`imageboard-cleanup.service` и `imageboard-media-monitor.service` сверь
пользователя `imageboard`, каталог проекта, интерпретатор и общий
`EnvironmentFile`. В cleanup и worker замени `/srv/imageboard-media` в
`RequiresMountsFor` и `ReadWritePaths` на фактический `MEDIA_STORAGE_ROOT`.
Пользователю сервиса нужны права на чтение кода и запись на медиатом.

```bash
sudo systemd-analyze verify /etc/systemd/system/imageboard-media-worker.service \
    /etc/systemd/system/imageboard-{cleanup,media-monitor}.{service,timer}
sudo systemctl daemon-reload
sudo systemctl enable --now imageboard-media-worker.service \
    imageboard-cleanup.timer imageboard-media-monitor.timer
systemctl list-timers 'imageboard-*'
sudo systemctl start imageboard-cleanup.service
sudo systemctl start imageboard-media-monitor.service
journalctl -u imageboard-media-worker -u imageboard-cleanup -u imageboard-media-monitor
```

Оба таймера срабатывают каждые пять минут и после простоя догоняют пропущенный
запуск. Cleanup удаляет истёкшие claims, обрабатывает задачи файловой очистки
и удаляет истёкшие сессии. systemd не запускает второй экземпляр активного
сервиса. При ошибке команды цепочка прерывается до следующего запуска.
Ошибки отдельных файлов остаются в очереди с действующим backoff.

`python -m scripts.monitor_media` выводит одну строку JSON в stdout.
При запуске systemd она попадает в journald. Команда проверяет идентификатор
тома, свободные блоки с учётом порога inode, учитываемые квотой файлы и резервы,
размер очередей, просроченные lease и текущие ошибки. `disk_headroom_bytes`
показывает запас после вычета свободного резерва, ожидаемых записей и
multipart-бюджета. `quota_headroom_bytes` показывает запас квоты после учтённых
байтов и multipart-бюджета.

Код завершения `0` означает штатный снимок. Код `1` означает предупреждение
и отражается как ошибка запуска в systemd. Причины перечислены в `warnings`:

- использовано не менее 90% квоты или закончился запас для записи на том
- в очереди есть обработка или очистка старше 15 минут либо просроченный lease
- есть окончательно неудачные обработки, повторные попытки с ошибками или
  незавершённые задачи очистки с ошибками

Код `2` означает, что снимок получить не удалось. Проверь PostgreSQL,
миграции, монтирование и соответствие тома реестру. Для диагностики следи
за состоянием трёх сервисов и их журналом. Для API используй `/ready`.
Снимки показывают текущее состояние. История отдельных сбоев обработки
и очистки доступна в журналах worker и cleanup.

### проверка восстановления worker

Выполняй проверку на тестовом окружении с отдельными БД и томом. Загрузи тестовое
вложение и дождись `processing`. Останови worker через
`systemctl stop imageboard-media-worker`, затем запусти через
`systemctl start imageboard-media-worker`. Для проверки автоматического
перезапуска при аварии на том же тестовом окружении можно вместо остановки
завершить весь cgroup командой
`systemctl kill --kill-whom=all --signal=SIGKILL imageboard-media-worker`.
При аварии systemd запустит новый процесс через 10 секунд. Задача останется
в PostgreSQL до истечения 10-минутного lease, после чего worker подберёт её
снова. Сверь `ready`, производные файлы и исчезновение карантинного исходника
после cleanup. При исчерпании трёх попыток запись перейдёт в `failed`.
Интеграционный тест `test_media_worker_recovers_after_process_stop` останавливает
реальный процесс после частичной записи и ускоряет истечение lease в тестовой БД.

## дисковая квота медиахранилища

В production `MEDIA_STORAGE_ROOT` должен быть абсолютной точкой монтирования
отдельного локального Linux-тома. API, worker и cleanup используют один том,
общую БД и одинаковые настройки. Выдели том с гарантированной ёмкостью и
задай жёсткую квоту блоков средствами ФС или лимит тома с резервом блоков,
недоступных сервисным пользователям. Ёмкость должна покрывать лимит приложения,
свободный резерв и служебное место ФС. Не размещай на томе базы, логи и бэкапы.
Приложение также проверяет доступные блоки и inode. Для FFmpeg нужен `/usr/bin/prlimit`.

| переменная окружения | значение по умолчанию | назначение |
| --- | ---: | --- |
| `MEDIA_STORAGE_MAX_BYTES` | 8589934592 | общий предел файлов и резервов |
| `MEDIA_STORAGE_MIN_FREE_BYTES` | 268435456 | минимальный свободный резерв |
| `MEDIA_UPLOAD_MAX_FILE_BYTES` | 20971520 | предел файла от 1 до 100 МиБ, одновременно действует предел доски |
| `MEDIA_UPLOAD_CONCURRENCY` | 4 | число одновременных multipart-запросов на том |
| `MEDIA_UPLOAD_TIMEOUT_SECONDS` | 120 | общий срок приёма тела запроса |

Multipart-тело ограничено размером файла плюс 64 КиБ. Для каждого слота в
квоте предусмотрен этот максимум и запас блоков на каждый временный файл. Парсер
пишет в закрытый `.spool` на томе. Nginx передаёт upload потоком по HTTP/1.1.
Согласуй `client_max_body_size` с настройкой приложения и проверь загрузку с
chunked и временный каталог Nginx. Меняй лимиты при остановленной записи.

Для первичного запуска и обновления с 024 останови приём загрузок в Nginx,
API, worker, таймер очистки и активный сервис очистки. Смонтируй том,
примени миграции и выполни `python -m scripts.inventory_media_storage`
с настройками этого окружения.
Команда связывает БД с идентификатором тома, учитывает имеющиеся файлы и
выводит неизвестные пути. Файлы и публикации сохраняются. При заполнении новые
загрузки получат `503 media_storage_full`. Выдача и штатная очистка доступны.
После инвентаризации запускай API и worker на версии с квотой. При переносе
восстанавливай БД, реестр, файлы и идентификатор тома вместе.

Исходник и пиковый объём обработки резервируются до `201`. Временный MP4
ограничен 22 МиБ при прежнем пределе готового MP4 20 МиБ. Для WebP display
предел 32 МиБ, для анимации 128 МиБ, для обычного превью 2 МиБ. Для audio
действует 48 МиБ, для voice 6 МиБ. Форматные пределы стикеров сохраняются.
При нехватке места worker откладывает задачу, сохраняя бюджет обычных попыток.
После `ready` учёт исходника освобождается штатной очередью очистки.
При фиксации загрузки записанный исходник уже входит в измеренную занятость
тома. В расчёте будущих записей остаются только ещё не созданные файлы.
Если worker повторно оставит файл по тому же пути после исчерпания попыток,
очистка снова поставит путь в очередь и освободит резерв после удаления.
Неизвестные файлы требуют решения оператора.
После ручного переноса такого файла повтори инвентаризацию с `--reconcile`
при остановленных API, worker и cleanup. Команда снимет учёт отсутствующих
неизвестных файлов и сохранит резервы зарегистрированных операций.

## загрузка и выдача media

`/api/v1/media` остаётся выключенным, но `POST /api/v1/boards/{slug}/media`
принимает JPEG, PNG, static WebP, GIF, animated WebP, MP3, M4A/AAC, OGG/Opus
и MP4 с H.264 и необязательной дорожкой AAC. Загрузка требует действующего
posting claim. Файл попадает в закрытый quarantine, а worker перекодирует его
в производные файлы без исходных метаданных.

Готовое attached media получает opaque key. Запросы `GET` и `HEAD` к
`/media/{key}/preview|display|content` повторно проверяют `ready`, attach и
видимость доски, поста и треда в PostgreSQL. FastAPI возвращает заголовок
`X-Accel-Redirect`, а файл читает internal location Nginx. У quarantine и
оригиналов отсутствуют HTTP URL.
`deploy/nginx.conf.example` - шаблон, а не применённая конфигурация: оператор
должен заменить путь alias на абсолютный `MEDIA_STORAGE_ROOT`, закрыть права
storage и проверить Nginx отдельно.

Изображения, audio и voice используют `public, max-age=31536000, immutable`.
После скрытия новый запрос к приложению получает `404`, а уже закешированная
копия может оставаться доступной клиенту. Стикеры, видео и их превью используют
`no-store`. Сохрани эту политику на reverse proxy.

GIF и animated WebP проходят отдельные пределы worker: до 4 096 px по стороне
кадра, 8 миллионов пикселей на кадр, 300 кадров, 30 секунд и 100 миллионов
суммарно декодированных пикселей. Display перекодируется в animated WebP, preview
остаётся статичным WebP. Это серверная защита ресурсов, а не пределы Telegram.
По умолчанию действует предел 20 MiB на файл, 10 вложений и 200 MiB на пост.
Глобальную медиаполитику меняет owner через `/admin`. Admin и owner управляют
переопределениями досок. Пустое значение наследует глобальную настройку. В шаблоне
Nginx `client_max_body_size 21m` ограничивает весь multipart-запрос. При изменении
разрешённого размера файла согласуй предел Nginx с настройками сайта и досок.
Жёсткие ограничения форматов сохраняются при изменении общей настройки.

Audio MP3/M4A/AAC и voice OGG/Opus требуют system dependencies `ffprobe` и
`ffmpeg`, заданные через `FFPROBE_BIN` и `FFMPEG_BIN`; это обязательные
зависимости production и CI. FFprobe проверяет codec,
container, duration, channels и sample rate, а worker делает canonical derivative:
M4A/AAC для audio и OGG/Opus для voice. Лимиты Imageboard: audio до 30 минут,
voice до 10 минут, audio до двух каналов, voice строго один канал, sample rate до
48 kHz. Это не утверждения о лимитах Telegram. Production Nginx должен оставить
audio/voice locations `internal` и разрешать Range только для derivative файлов.

Для видео установи FFmpeg с энкодерами `libx264`, `aac` и `libwebp`. Движок
проверяет структуру MP4 и дорожки через FFprobe. Он принимает одну дорожку
H.264 и, при наличии звука, одну AAC до двух каналов и 48 kHz. Входное видео
ограничено 120 секундами, 1920×1080 или 1080×1920, 30 кадрами/с и
3 600 видеопакетами. Worker ограничивает время, потоки, размер кадра,
максимальную единичную аллокацию FFmpeg и размер канонического MP4 до 20 MiB.
На время выполнения FFmpeg отключены внешние ссылки MP4 и сетевые протоколы.
Готовые файлы содержат H.264/yuv420p 30 кадров/с, AAC-LC с частотой 48 кГц при наличии звука и
`faststart`. Статичный WebP до 320×180 создаётся из первого кадра канонического
видео. Worker проверяет готовый MP4 и сохраняет параметры из него. Замена обоих
файлов выполняется под блокировкой текущей задачи. Состояние `ready` и задача
очистки исходника фиксируются в одной транзакции. Для нового окружения и для
обновления примени миграцию `021_video_media` обычной командой мигратора.
[Документация FFmpeg](https://ffmpeg.org/ffmpeg.html)

Внутренний тип `video_note` использует тот же worker с пределами 60 секунд и
640×640, квадратным кадром и бюджетом 1 800 видеопакетов. Будущий Telegram-бот
будет задавать этот тип из проверенного Telegram update и публиковать через
доверенный серверный код. Публичная форма и публичные posting claims дают
клиенту работать с обычным видео.
[Telegram Bot API](https://core.telegram.org/bots/api#sendvideonote)

Миграция `022_static_stickers` добавляет внутренний тип `sticker`. Публичная
загрузка WebP сохраняет тип `image`. Доверенный адаптер передаёт связанный
аккаунт, существующий тред и статический WebP до 512 КиБ с длинной стороной
ровно 512 px. Для адаптера нужны проверка источника Telegram update,
привязка аккаунта и собственный транспортный антиспам.

Worker повторно проверяет quarantine, создаёт один WebP display с сохранением
альфа-канала и убирает входные метаданные. Он заменяет файл под текущим lease,
а `ready` и задачу очистки quarantine записывает одной транзакцией. Для доставки
используется internal location `/_imageboard_media/stickers/` с alias на каталог
`display` и `Cache-Control: no-store`. При обновлении примени этот location из
`deploy/nginx.conf.example`, чтобы повторные запросы проходили проверку видимости.
Публичный `display_url` появляется после атомарной публикации ответа с одним
стикером и пустым текстом. При истечении claim или удалении поста либо треда
cleanup queue удаляет файлы.

Миграция `023_animated_stickers` расширяет тот же claim на TGS. Движок
принимает один gzip-поток до 64 КиБ, распаковывает не более 1 МиБ JSON и
проверяет холст 512×512, длительность до 3 секунд и частоту до 60 кадров/с.
Проверка ограничивает глубину JSON 32 уровнями и общее число узлов 100 000
с учётом удаляемых метаданных. После разворачивания ссылок допустимы до
256 слоёв, 200 000 узлов и глубина до 8 вложенных композиций или родительских
связей. Поддерживаются векторные shape-слои, null-слои и вложенные векторные
композиции. Ссылки на композиции разрешены только на слоях типа precomp.
Проверка отклоняет циклы, управляющие символы в именах JSON-полей, внешние и
растровые ресурсы, текст, выражения, маски, эффекты и повторители. Канонический
gzip хранит нормализованный JSON без имён и метаданных экспортера.
[Формат TGS](https://core.telegram.org/api/stickers)

Установи `librlottie0-1` и `util-linux` на Ubuntu 24.04. CI использует эти
пакеты на `ubuntu-24.04`. Воркер проверяет C API библиотеки при запуске
рендера. Утилита `/usr/bin/prlimit` задаёт стек в 1 МиБ до запуска Python
и создания потоков rlottie. Worker запускает отдельный процесс для рендера
первого кадра и кодирования WebP. На процесс выделено 512 МиБ адресного
пространства, 3 секунды CPU и 8 секунд общего времени. Выход ограничен 512 КиБ.
Процесс получает вход и выход через стандартные потоки. Вместо окружения worker
он получает только ограничение аллокатора glibc и запускается без core dump.
При ошибке рендера временные файлы удаляются, а задача проходит обычный
retry/failed. Перед публичным запуском нужны актуальные исправления безопасности
rlottie и изоляция воркера на уровне ОС. Ограничения процесса задают бюджет
ресурсов. [Исходный код rlottie](https://github.com/Samsung/rlottie)
[Уведомление Ubuntu о безопасности rlottie](https://ubuntu.com/security/notices/USN-8559-1)

Для TGS установи locations `/_imageboard_media/stickers/*.tgs` и
`/_imageboard_media/sticker-previews/*.webp` из шаблона. Оба пути должны быть
internal. Для анимации отдавай MIME `application/x-tgsticker` и байты gzip
как содержимое файла. В JSON ответа поста эти производные доступны по
`content_url` и `preview_url`. Оба запроса используют `Cache-Control: no-store`.
Файлы публикуются под одним lease. При удалении поста или истечении claim
очередь очистки учитывает оба конечных пути даже после остановки worker до commit.

Миграция `024_video_stickers` добавляет WebM в тот же внутренний поток для
будущего Telegram-адаптера. Принимается до 256 КиБ, одна дорожка VP9 без звука,
длинная сторона ровно 512 px, до 3 секунд и 30 кадров/с. Worker повторно
проверяет источник, включая интервалы между кадрами и предел в 90 кадров.
Ошибка демультиплексирования отклоняет файл даже при частичном выводе FFprobe.
При отсутствии длительности в контейнере предел проверяется по пакетам.
Worker перекодирует видео с сохранением декодированного альфа-канала,
проверяет размер, частоту и временные метки готового WebM и создаёт статичный
WebP из первого кадра результата. Для канонического WebM также действует
предел 256 КиБ. При превышении worker пробует более сильное сжатие.
Файл с заявленной альфой отклоняется, если декодер не возвращает альфа-канал.
FFmpeg и FFprobe запускаются с ограничениями времени и размера выделения
памяти. `/usr/bin/prlimit` задаёт до 768 МиБ адресного пространства,
12 секунд CPU и 2 МиБ на файл. У FFmpeg также ограничены потоки и число
пикселей в декодируемом кадре.
В сборке FFmpeg нужны декодер и энкодер `libvpx-vp9` и энкодер `libwebp`.
Пути к бинарникам задаются через `FFMPEG_BIN` и `FFPROBE_BIN`.
[Спецификация контейнера WebM](https://www.webmproject.org/docs/container/)

Установи internal location `/_imageboard_media/stickers/*.webm` с MIME
`video/webm` и поддержкой одного Range. WebP использует существующий
`sticker-previews`. FastAPI повторно проверяет видимость перед выдачей каждой
производной с `Cache-Control: no-store`. После истечения claim или удаления
очередь очищает оба файла, включая пути, которые worker успел заменить до commit.
Публичная форма WebM не принимает.

Для воспроизведения Nginx читает канонический файл из внутреннего
`/_imageboard_media/video/` и обрабатывает один Range за запрос. Превью читается
через отдельный internal location `/_imageboard_media/video-previews/` с alias
на каталог `previews`. Для обоих маршрутов сохрани `Cache-Control: no-store`,
чтобы после скрытия или удаления новый запрос снова проверял видимость в API.
Выдай worker и Nginx права на соответствующие операции с производными файлами,
а доступ к исходникам оставь приложению и worker. Проверь Nginx с теми же
пользователями и правами, которые будут использоваться при запуске.
[Документация Nginx](https://nginx.org/en/docs/http/ngx_http_core_module.html#max_ranges)

Запрещённые контейнеры и неподдерживаемые дорожки MP4 возвращают
`415 unsupported_media_type`. Повреждённый допустимый кандидат или превышение
технического лимита возвращает `422 invalid_media`. Нарушение, обнаруженное
при полном декодировании, проходит очередь retry/failed.

До эксплуатации публичной загрузки нужны:

- проверка квот и фоновой очистки на выбранном Linux-томе;
- базовый мониторинг;
- изоляция медиаворкера, действующие ограничения ресурсов и проверка выдачи через Nginx;
- операционные проверки worker, восстановления после файловой ошибки и нагрузки;
- разбор зависших временных файлов после принудительной остановки worker.

Файлы проходят обработку с `NoopMediaScanner` без реального антивирусного
сканирования. ClamAV отложен. Интерфейс `MediaScanner` сохранён для будущей
проверки quarantine-файла до перехода в `ready`.

## realtime

Маршрут `/api/v1/ws` выключен по умолчанию. Для стенда примени
`026_realtime_outbox`, задай `REALTIME_ENABLED=true` и перечисли точные
браузерные origins через запятую в `REALTIME_ALLOWED_ORIGINS`. Используй
одинаковый `REALTIME_CHANNEL` во всех процессах одного сайта и отдельный канал
для каждого сайта или стенда на одном Redis. Pub/Sub разделяет каналы по имени
и использует их во всех Redis database. Миграция добавляет триггеры записи в
outbox в транзакциях контента и видимости. Процессы API обслуживают очередь
даже с выключенным публичным маршрутом.

Nginx должен пропускать Upgrade и держать соединение в ожидании дольше
heartbeat. Шаблон systemd ограничивает кадр на уровне Uvicorn до 2 КиБ и
очередь приёма до четырёх сообщений. Сервер допускает 100 соединений на процесс,
32 области на клиента и 20 команд за скользящую секунду. Он отправляет
`ping` через 30 секунд, ждёт `pong` до 10 секунд и ограничивает отдельную
отправку пятью секундами. Переполнение очереди отправки из 64 сообщений закрывает
соединение. Для запуска вне systemd передай те же флаги Uvicorn.

После обрыва Redis API восстанавливает подписку и закрывает затронутые
WebSocket с кодом `1013`. Клиенты переподписываются с задержкой и сверяются
с REST. Публикация из outbox допускает повторы. При полном отказе Redis
существующие Redis-зависимые проверки HTTP, включая антиспам, также лишаются
своей зависимости.

В journald проверь сообщения о состоянии Redis-подписки, повторных попытках,
возрасте очереди и причинах закрытия соединений. Для контроля очереди можно
собирать число записей и возраст старейшей запросом
`SELECT count(*), now() - min(created_at) FROM realtime_outbox`. Перед
включением на целевом контуре проверь WSS, Origin, переподключение при отказе
Redis и нагрузку нескольких процессов одновременно с REST. Протокол клиента
описан в [README](../README.md#realtime).

## что проверять после настройки сервера

1. `/health` отвечает без базы, а `/ready` отвечает только когда доступны
   PostgreSQL и Redis
2. Nginx передаёт настоящий IP только с локального proxy, а `TRUSTED_PROXY_IPS`
   содержит только этот адрес
3. cookie сессии в production имеет `Secure`, а `APP_DEBUG=false`
4. timer очистки сессий и резервные копии действительно запускаются по расписанию
5. восстановление последней резервной копии проходит в отдельной тестовой базе
6. Готовый MP4 по `GET /media/{opaque key}/content` отдаёт `206` и
   `Content-Range` на запрос `Range: bytes=0-31`. Прямой внутренний URL и opaque
   URL после скрытия поста или треда возвращают `404`
7. Статический стикер по `GET /media/{opaque key}/display` отдаёт WebP с прозрачностью.
   Для TGS `/preview` отдаёт прозрачный WebP, а `/content` отдаёт канонический gzip
   с MIME `application/x-tgsticker`. Для WebM `/preview` отдаёт первый кадр с
   прозрачностью, а `/content` возвращает `video/webm` и поддерживает один Range
   с ответами `206` для доступного и `416` для недоступного диапазона.
   Для всех файлов `HEAD` возвращает те же
   заголовки без тела, GET и HEAD возвращают
   `Cache-Control: no-store`. Прямой внутренний путь и публичный URL после
   скрытия или удаления возвращают `404`
